# Coding AgentとObsidian CLIによるObsidianプラグインのE2Eテスト

Coding Agentによる、Reading Annotationプラグインの実機検証手順。テスト対象はObsidian CLIを使った注釈作成、保存内容と表示の確認、証拠保存、後片付けまでの操作。ユーザーはテスト用vaultの登録、エージェントの担当は環境準備と登録後の検証。

## 基本ルール

### エージェントによる継続的な改善

Coding Agentの担当は、テストの実行と、実行に必要な指示・コードの作成および改善。
不足や曖昧さの発見時は、原因の確認、必要な変更、変更後の検証までの対応。
共通手順はこの文書、ケース固有の指示は`caseDir`、実行コードは`e2e/scripts`への反映。

### 決定論的なテストへの段階的な移行

初期段階は、プロンプトによる操作指示とエージェントの判断での実行。
繰り返し実行する操作と、期待結果が明確になった判定から、固定データ・実行コード・アサーションへの移行の検討。
移行単位はケース内の操作・判定ごと。移行前後の確認範囲と結果の照合。
コード化した処理はスクリプトでの実行、未移行部分はエージェントによる対応。

### 自動テスト失敗時のエージェントによる対応

自動テストは不一致や実行エラーの検出と、失敗箇所での停止。
停止後はCoding Agentによる証拠確認、実装変更との照合、原因調査と対応。
期待する動作が同じ場合は期待結果の維持、操作方法や要素の取得方法の変更への追随。
期待結果の変更は、確認できた仕様変更を根拠とする更新。成功扱いにするためだけの判定緩和は不可。
修正後は同じケースの再実行と、初回失敗・変更内容・再実行結果の記録。

## 前提条件と完了条件

### テスト対象

対象はこのリポジトリのReading Annotationプラグイン。

### 必要な環境

| 環境             | 必要な状態                                                    |
| ---------------- | ------------------------------------------------------------- |
| Obsidian Desktop | 起動済み                                                      |
| Obsidian CLI     | インストール・有効化済み                                      |
| Coding Agent     | ローカルコマンドの実行とファイルの作成・削除が可能な状態      |
| 開発環境         | `mise`経由のNode.js・pnpm実行環境、依存関係のインストール済み |
| テスト用フォルダ | 普段のノートを含まない、上書き・削除可能な専用領域            |

CLIの導入方法は[Obsidian公式CLI資料](https://help.obsidian.md/cli)。

### 検証済みバージョン

| 項目                    | 検証済みの値        |
| ----------------------- | ------------------- |
| 検証日                  | 2026-10-02          |
| OS                      | macOS 27.0.1、arm64 |
| Obsidian本体・installer | 1.13.7              |
| Node.js                 | 24.21.0             |
| pnpm                    | 12.8.1              |

### テスト終了時に得る結果と証拠

共通で残す情報。

| 項目     | 内容                                     |
| -------- | ---------------------------------------- |
| 実行条件 | 対象コード、実行環境、vaultの絶対パス    |
| ケース   | ケースID、操作、期待値、実測値、判定結果 |
| 証拠     | 保存内容、DOMの確認結果、ログ、画面画像  |
| 後片付け | 削除結果、残したデータと設定             |

成功条件は以下の通り。

- 操作の完了
- 保存内容と期待値の一致
- 表示と期待値の一致
- 未処理エラーの不在

失敗条件は以下の通り。

- 操作の失敗
- タイムアウト
- 期待値との不一致
- 未処理エラーの発生

#### テストケースの結果判定ルール

- 既知の不具合による期待値との不一致も失敗として記録
- 未実施・証拠不足の場合は理由付きで記録し、成功判定の対象外
- CLIの終了コード0だけによる成功判定は不可

## 1. ローカル設定の準備

エージェントによる、リポジトリのルートでの実行。
設定検証はTypeScript、ケース操作はBash。セッション読み込み後の操作は、同じBashセッションでの継続。

### 設定ファイルの作成

[作成スクリプト](../e2e/scripts/init-config.ts)による、雛形からの`e2e/config.json`の作成。既存設定がある場合は保持。

```bash
mise exec -- node e2e/scripts/init-config.ts
```

### 接続先と保存先の指定

エージェントによる、`e2e/config.json`の各項目の確認・編集。

| 設定項目            | 指定内容                                                        |
| ------------------- | --------------------------------------------------------------- |
| `obsidianCommand`   | CLIのコマンド名、または実行ファイルの絶対パス。引数は指定対象外 |
| `obsidianVaultPath` | テスト専用vaultの絶対パス                                       |
| `caseDir`           | ケースの保存先。リポジトリ基準の相対パス、例は`e2e/cases`       |
| `reportDir`         | 結果の保存先。リポジトリ基準の相対パス、例は`reports/e2e`       |

### 設定の読み込みとCLIの確認

[セッションスクリプト](../e2e/scripts/session.sh)経由での[設定検証](../e2e/scripts/load-config.ts)と共通関数の読み込み。
成功時は設定値の読み込み、失敗時は設定の修正。

```bash
bash
source e2e/scripts/session.sh
```

読み込み成功後のCLIの確認。

```bash
check_cli
```

読み込み後に使用する変数。

| 変数               | 内容                            |
| ------------------ | ------------------------------- |
| `REPO`             | リポジトリの絶対パス            |
| `OBSIDIAN_COMMAND` | `obsidianCommand`の値           |
| `TEST_VAULT`       | `obsidianVaultPath`の値         |
| `TEST_VAULT_NAME`  | vaultのパス末尾から取得した名前 |
| `CASE_DIR`         | `caseDir`から取得した絶対パス   |
| `REPORT_ROOT`      | `reportDir`から取得した絶対パス |
| `PLUGIN_ID`        | `manifest.json`の`id`           |

各コマンドの終了コードと出力の確認、失敗時の後続操作の停止。
準備・接続確認・後片付けの実装は[手順スクリプト](../e2e/scripts/workflow.sh)。

エージェントによる、`CASE_DIR`配下のMarkdownファイルからの実行対象ケースの選択とIDの記録。
以下のコマンドによるケースファイル一覧の確認。

```bash
list_cases
```

以下の表は既定の`e2e/cases`のケース一覧。
`caseDir`変更時の実行対象は、設定先のケースファイル。
各ケースファイルで管理する、初期状態・操作・期待結果・証拠・後片付け。
ケース固有の期待値と操作の変更先は、各ケースファイル。

| ID  | ケース                                                                |
| --- | --------------------------------------------------------------------- |
| A   | [注釈追加後のエディタ更新](../e2e/cases/editor-create.md)             |

| E   | [ノート切替時の子コンポーネント数](../e2e/cases/panel-lifecycle.md)   |

各ケースの結果は`REPORT`配下のID別ディレクトリへの保存。
同じIDの再実行も別ディレクトリ、ケース定義への実行結果の書き込みは対象外。

### CLI・内部APIで操作する範囲の明示

| 操作             | 使用する経路                    |
| ---------------- | ------------------------------- |
| vault登録        | ユーザーによるObsidianのGUI操作 |
| ノートを開く操作 | Obsidian CLIの`open`            |
| テキスト選択     | `eval`経由のエディタAPI         |
| 注釈コマンド     | Obsidian CLIの`command`         |
| Submitボタン     | `eval`経由のDOM要素の`click()`  |
| 保存・表示の検証 | Vault API、DOM、CLIのログ取得   |

この経路での検証対象は、起動中のObsidianとプラグインを通じた保存・表示の連携。
物理的なマウス操作、キーボード操作、ショートカットの割り当ては対象外。

## 3. 専用vaultとプラグインの準備

### テストデータの作成とビルド成果物の配置

エージェントによる、型検査を含むビルドと専用フォルダの作成。
配置先は`e2e/config.json`の`obsidianVaultPath`で指定した専用フォルダ。
既存フォルダの再利用時には、上書き対象のノートと設定の事前確認。

```bash
prepare_vault
```

`git diff`の対象外となる未追跡コードがある場合は、そのコードの別途保存。
固定ノート3件の上書き、プラグイン一覧の専用設定への置き換えを伴う準備。
`main.js`・`manifest.json`・`styles.css`の配置方法は、作業コピーへのsymlink。

### 未登録の場合のユーザーへの登録案内

エージェントによる、登録済みvault一覧と登録対象パスの取得。

```bash
show_registration
```

名前と絶対パスが一致する登録済みvaultの場合は、登録工程の省略。
未登録の場合は、エージェントからユーザーへの絶対パスと操作方法の案内。
macOSでの管理画面の表示。

```bash
open_vault_manager
```

| 順序 | ユーザーの操作                           |
| ---- | ---------------------------------------- |
| 1    | 「Open folder as vault」の「Open」の選択 |
| 2    | フォルダ選択画面での`⌘⇧G`の押下          |
| 3    | 案内された絶対パスの入力とEnterの押下    |
| 4    | 「Open」によるvault登録                  |
| 5    | エージェントへの登録完了の連絡           |

初回の信頼確認ダイアログが表示された状態でも、登録完了の連絡は可能。
エージェントによる登録操作の自動化は対象外。
未登録の場合の後続操作は、ユーザーの完了連絡後の再開。

## 4. 接続先とプラグインの読み込みの確認

### ユーザーの登録完了後の絶対パス照合

エージェントによる、対象vaultの絶対パスの照合。
不一致や`Vault not found.`の場合は、そのvaultへの変更操作の停止。

```bash
verify_vault
```

[操作スクリプト](../e2e/scripts/obsidian.sh)の関数による、対象vaultへの操作。
`obs`でのエラー出力検査、`js`での読み取り専用評価、`run_js`での変更操作の実行。
空応答の再試行対象は読み取りだけ、変更操作は操作ID付きの1回の送信。

条件待機は最大40回、各回の待ち時間は250ミリ秒。
実際の待機時間には、CLI応答時間と読み取り再試行の加算。
一時変数を共有するため、同じvaultでの実行は直列処理。

### プラグインの有効化とコマンド登録の確認

エージェントによる成果物の存在確認と、restricted modeの解除。
解除に伴うvault再読み込み後の接続待ち。

```bash
load_plugin
```

ロード済みのプラグイン実体と注釈コマンドの存在を、開始条件として確認。
起動時エラーの検出時には、再読み込み前の証拠保存と調査。

## 5. テストケースの実行

### ケースごとの初期化

[操作スクリプト](../e2e/scripts/obsidian.sh)の`reset_case`による初期化と、`capture_evidence`による証拠保存。
`capture_evidence`の実行ごとに、新しい保存先の作成。
CLI経由での取得失敗は`capture-errors.txt`への記録。

初期化による削除対象は`42-annotation/`内の`Sample.md`・`Other.md`・`Moved.md`と、専用vaultのMarkdownタブ・注釈パネル。
未処理エラー検出時は、初期化前の証拠保存。

### CLIによる操作と非同期処理の完了待機

エージェントによる、選択したケースファイルのコードブロックの順次実行。
ケース冒頭での`CASE_ID`と`CASE_REPORT`の設定、初期化後の操作開始。
同じvaultでのケース実行は直列処理。

`run_js`による変更操作の完了確認後、ケースで指定した保存内容と表示の条件待機。
待機上限到達時は、変更操作の再送前に状態とエラーの保存。

### 表示・保存内容・エラーの確認

各ケースの期待結果と実測結果の照合。
対象ノート・ペイン・表示モードを限定したDOM件数の確認。
非表示のエディタと閲覧モードの件数の合算は対象外。

判定後と失敗時の`capture_evidence`による証拠保存。
保存した画像での表示確認と、`CASE_REPORT`内の`result.md`への合否記録。
全条件成立時の合格、一部でも不一致の場合の不合格、未実行時の未実施。

## 6. 失敗時の証拠保存と再現確認

### ログ・画像・実行条件の保存

エージェントによる、失敗したコマンド、その出力、期待結果、実測結果の記録。
失敗時の追加記録は、再現手順と再実行結果。再実行できない場合は、その理由の記録。
初期化やプラグイン再読み込みの前に、失敗時点の証拠保存。

```bash
capture_evidence
```

CLIに接続できない場合は、取得できたファイルと接続エラーの保存。
操作が完了したか不明な場合は、注釈ファイルと画面の読み取り確認。
画面画像だけ、またはCLIの終了コードだけによる原因の断定は保留。

### エージェントによる原因調査と対応

証拠保存後の、失敗した操作・判定と現在の実装の照合。
自動テストの失敗だけでは確定しない、製品の不具合とテスト側の追随漏れの区別。

| 確認できた原因                               | エージェントの対応                                 |
| -------------------------------------------- | -------------------------------------------------- |
| 接続先・初期状態の不備                       | 設定・準備処理の修正                               |
| 実装変更による操作方法・要素の取得方法の変化 | 期待結果を維持した指示・テストコードの更新         |
| 製品の期待動作との不一致                     | 不具合の記録と、依頼範囲に応じた製品修正または報告 |
| 仕様変更による期待動作の変化                 | 変更根拠の記録と、ケース・判定コードの更新         |
| 原因や期待動作が不明                         | 追加調査と、判断に不足する情報のユーザーへの確認   |

修正対象に応じた型・構文検査と、変更した操作・判定の動作確認。
再利用できる調査結果の、手順・ケース・スクリプトへの反映。

### 初期状態からの再実行

初回結果の保存後、エージェントによる同じ条件での再現確認。
先の非同期操作が`pending`の場合は、操作の状態確認まで再実行の保留。

```bash
operation_status
```

前の操作の完了確認後、保存済みエラーのクリアと初期化。
Submit後もモーダルが残る場合は、閉じる操作後の再実行。

```bash
retry_case
```

再実行対象は、ノートを開く操作から保存内容・表示・エラー確認までの一連の操作。
再実行時の証拠は別の保存先、初回の失敗結果は保持。
再現なしの場合も、初回失敗と再実行成功の両方の報告。

## 7. 後片付けと結果報告

### 生成データと一時状態の削除

エージェントによる、証拠保存後の生成注釈・タブ・一時変数の削除。
失敗時の後片付けも、非同期操作の完了確認後の実行。
モーダルが残る場合は、モーダルを閉じてからの実行。

```bash
cleanup
```

次回用に残す対象は、専用vaultの登録、固定ノート、プラグインへのsymlink、有効化設定。
CLI接続失敗などによる未削除データがある場合は、対象パスと未完了理由の報告。

### 合否・既知の不具合・未確認範囲の報告

エージェントによる、`REPORT`ディレクトリへの`result.md`の作成。
以下の項目への実測値の記入と、ユーザーへの結果報告。

| 項目         | 記入内容                                                |
| ------------ | ------------------------------------------------------- |
| 実行条件     | コミット、未コミット変更、各バージョン、vaultの絶対パス |
| ケースID     | 初期状態、実行操作、期待結果、実測結果                  |
| 判定         | 合格・不合格・未実施と、その根拠                        |
| 証拠         | リポジトリ内のログ・保存内容・画像へのリンク            |
| 再現確認     | 失敗した操作、再現手順、初回と再実行の結果              |
| 改善内容     | 変更した指示・コード、変更理由、変更後の検証結果        |
| 自動化状況   | コード化した操作・判定、エージェントによる確認部分      |
| 既知の不具合 | 今回の結果との対応と、該当Issueへのリンク               |
| 未確認範囲   | 未実施のケースと操作経路                                |
| 後片付け     | 削除結果、残したデータ・設定、未完了の作業              |

合格範囲は、実行したケースで確認できた操作経路と期待結果。
未実施ケース、物理的なマウス・キーボード操作、別OSでの動作は未確認範囲としての報告。
